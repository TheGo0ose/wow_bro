# OTP-сервис — ТЗ 6, Осенний хакатон INAI 2026

REST API выдачи и проверки одноразовых 6-значных кодов с защитой от перебора и спама.
Python 3.10+, FastAPI. Состояние хранится в памяти процесса (по умолчанию) или в **Redis с TTL**.

## Запуск одной командой

```bash
pip install -r requirements.txt && python -m otp_service
```

Сервис слушает `http://127.0.0.1:8000` (хост и порт задаются через `OTP_HOST` и `OTP_PORT`).

С Redis (если он уже запущен на `localhost:6379`):

```bash
OTP_STORAGE=redis python -m otp_service
```

Через Docker (сервис + Redis):

```bash
docker compose up --build
```

Тесты (92 штуки, около 5 секунд; Redis-тесты идут на fakeredis, поднимать Redis не нужно):

```bash
python -m pytest -q
```

## API

| Метод | Тело | Ответы |
|---|---|---|
| `POST /otp/send` | `{"msisdn": "996770730000"}` | **200** выдан · **400** формат · **423** номер заблокирован · **429** лимит выдачи |
| `POST /otp/verify` | `{"msisdn": "996770730000", "code": "012345"}` | **200** верно · **400** формат · **401** неверный / нет кода / уже использован · **410** истёк · **423** заблокирован · **429** IP-лимит |
| `GET /dashboard` | | дашборд событий безопасности (бонус) |
| `GET /security/events` | | последние события и счётчики в JSON (без кодов, номера замаскированы) |
| `GET /health` | | проверка, что сервис жив |

Ответы 429 и 423 содержат заголовок `Retry-After`.

**Доставка SMS.** Каждая выдача дописывается одной строкой JSON в `outbox/sms.jsonl`
(путь можно изменить через `OTP_OUTBOX`):
`{"ts": "2026-11-21T09:00:00+06:00", "msisdn": "996770730000", "code": "012345"}`.
Сервис этот файл не читает. Публичного метода «получить код» нет.

## Что реализовано (пункты «Обязательно»)

| Требование | Где и как |
|---|---|
| 6 цифр из криптостойкого генератора | `codes.secure_code()`: `secrets.randbelow(10**6)` с ведущими нулями, `000000` допустим |
| Срок жизни 120 с, код одноразовый | `elapsed >= 120` даёт 410; после успешной проверки код сразу гасится |
| Новый send аннулирует прежний код | у номера хранится только один активный OTP |
| Хранится только HMAC, сравнение за постоянное время | HMAC-SHA256(`OTP_SECRET`, `msisdn:otp_id:code`) + `hmac.compare_digest` |
| Прогрессивная задержка 30 / 60 / 120 с, не больше 3 send за 10 минут | скользящее окно `(t−600, t]`, у каждой выдачи запоминается её ступень |
| 5 неверных вводов — блокировка на 15 минут | пятый неверный ввод уже даёт 423, блокировка действует на `[t, t+900)`; send тоже 423 |
| IP-лимит: 20 проверок в минуту | окно `(t−60, t]`, 21-й запрос получает 429; проверяется **первым**, до формата, кода и блокировки |
| Из параллельных verify с верным кодом успешен ровно один | сравнение HMAC, затем атомарное погашение по `otp_id` (compare-and-set): в памяти под `threading.Lock`, в Redis одним Lua-скриптом |
| Журнал безопасности без кодов | `logs/security.jsonl`; журнал физически отказывается писать поле `code` |
| `attack.py` | перебор по одному номеру, распределённый перебор по 50 номерам, подмена `X-Forwarded-For` |

**Бонусы:** хранение в Redis с TTL, дашборд событий, Docker Compose.

## Хранилище Redis (бонус)

Включается переменной `OTP_STORAGE=redis`. Бизнес-логика одна и та же: `service.py` работает
через интерфейс `Store`, а за ним стоит `MemoryStore` или `RedisStore` (`storage.py`).

- **Атомарность.** Каждая операция (выдача, IP-лимит, получение кода, погашение, неверный ввод)
  выполняется одним Lua-скриптом. Redis выполняет скрипт целиком, поэтому гонок нет даже при
  нескольких репликах сервиса над одним Redis. Есть тест: 4 «реплики», 40 параллельных verify
  с верным кодом дают ровно `200×1, 401×39`.
- **Только хеш.** В Redis лежит HMAC кода в hex. Тест проверяет, что открытого кода нет ни
  в одном ключе.
- **TTL на всех ключах:**

  | Ключ | Тип | Содержимое | TTL |
  |---|---|---|---|
  | `otp:otp:{msisdn}` | HASH | `id`, `hash`, `issued`, `failures` | 120 с + 1 ч (чтобы отвечать 410) |
  | `otp:sends:{msisdn}` | ZSET | выдачи в окне со ступенью | 10 мин + 1 мин |
  | `otp:lock:{msisdn}` | STRING | время конца блокировки | 15 мин + 1 мин |
  | `otp:ip:{ip}` | ZSET | verify-запросы с IP | 1 мин + 1 мин |

  TTL служит только для уборки мусора и всегда чуть длиннее логического срока. Сами решения
  принимаются по часам сервиса, которые передаются в скрипт. Поэтому подменяемые часы
  тестового режима работают и с Redis.
- `{msisdn}` в фигурных скобках — hash tag: ключи одного номера попадают в один слот
  и работают в Redis Cluster.
- Все тесты и все 24 сценария гоняются на обоих хранилищах.

## Проверка сценариями (формат жюри)

Сервис поддерживает **тестовый режим** с подменяемыми часами, чтобы сценарии с ожиданием
на 120, 600 и 900 секунд проходили мгновенно:

```bash
OTP_TEST_MODE=1 OTP_TRUSTED_IP_HEADER=X-Test-Client-IP python -m otp_service
```

```bash
python scenario_runner.py scenarios/scenarios_examples.json scenarios/extra_scenarios.json
```

Результат: **24/24**. Это 5 открытых сценариев жюри (O01, O03, O07, O12, O16) и 19 наших
(X02–X22): граничные 119.999 и 30 с, ступени 60 и 120 с, очищение окна, снятие блокировки,
IP-лимит, ошибки формата, распределённая атака, параллельные send.

Только в тестовом режиме и только с loopback-адреса доступны:
- `POST /__test__/advance {"seconds": 120}` — перемотать часы;
- `POST /__test__/reset` — сбросить состояние.

Код они не возвращают. В обычном режиме эти пути отвечают 404.

**Как определяется IP клиента.** По умолчанию берётся только из TCP-соединения. В uvicorn
отключён `proxy_headers`, поэтому `X-Forwarded-For` не читается (есть регрессионный тест).
Заголовку `OTP_TRUSTED_IP_HEADER` сервис верит, только если он явно включён в конфиге и запрос
пришёл от адреса из `OTP_TRUSTED_PROXIES` (по умолчанию `127.0.0.1` и `::1`). Через этот
механизм тестовый стенд передаёт `client_ip` из сценариев.

## Атака

```bash
python attack.py
```

Скрипт атакует только localhost. Между атаками он ждёт 61 с, чтобы очистилось окно IP-лимита.
Результат на реальных часах, по 1000 попыток в каждой атаке:

| Атака | Ответы | Что остановило |
|---|---|---|
| Перебор кода для одного номера | 401×4, 423×16, 429×980 | блокировка номера на 5-й попытке, IP-лимит на 21-й |
| Перебор по 50 номерам с одного IP | 401×19, 423×1, 429×980 | IP-лимит на 21-й попытке |
| То же с подменой `X-Forwarded-For` | 401×19, 423×1, 429×980 | IP-лимит: подмена заголовка не помогает |

Угадано кодов: **0**. Единственный 423 во второй и третьей атаке — это номер, который
заблокировала первая атака.

## Решения по неоднозначным местам ТЗ

- **Ступени задержки.** Задержка после выдачи определяется её порядковым номером в окне:
  после 1-й — 30 с, после 2-й — 60 с, после 3-й — 120 с. Пример: выдачи в 0, 450 и 510 с.
  В 600 с первая выходит из окна, но следующий send разрешён только в 630 с.
- **Неверный код для истёкшего OTP** даёт 410, счётчик ошибок не растёт.
- **Счётчик ошибок привязан к активному OTP.** Новый send начинает его с нуля.
  Перебор это не облегчает: send ограничен 3 выдачами за 10 минут.
- **При блокировке активный код аннулируется.** После снятия блокировки нужен новый send,
  старый код даёт 401.
- **Отклонённые по IP-лимиту запросы (429) в окно не засчитываются.**
- **В тестовом режиме** новый код всегда отличается от предыдущего. Так сценарии вида
  «новый send аннулирует старый код» детерминированы (это разрешено уточнениями).

## Что не успели и ограничения

- Redis-хранилище проверено на fakeredis (тот же Lua-интерпретатор), но не на настоящем
  Redis-сервере: на машине разработки его не было.
- Docker-образ написан, но на машине разработки не собирался (Docker не запустился).
- С `OTP_STORAGE=memory` нужен ровно один процесс uvicorn. С Redis можно запускать несколько.
- В Redis запись об истёкшем коде живёт 1 час. После этого проверка отвечает 401, а не 410.
- В Docker тестовый режим требует указать в `OTP_TRUSTED_PROXIES` адрес шлюза docker-сети:
  запросы с хоста приходят не с 127.0.0.1.
