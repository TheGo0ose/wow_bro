# План реализации: Production OTP-сервис + телеком-контур (ТЗ 6)

**Главная стратегия (под критерии 100 баллов):** Сначала гарантированно закрываем 80 базовых баллов — автопроверку (40), обязательные пункты (20) и качество кода с тестами (20). Затем делаем лёгкий и надёжный SOC-дашборд для бонусов (до 10 баллов) и только после стабильного тега `v1-core-passing` подключаем телеком-контур (`Jasmin + RabbitMQ + SMPPSim + биллинг`) под отдельным Docker Compose профилем.

> **Ключевой принцип архитектуры:** По умолчанию `docker compose up --build -d` поднимает только `otp-api` и `redis` за пару секунд — это гарантирует стабильный запуск на автопроверке жюри. Телеком-контейнеры вынесены в `profiles: ["telecom"]` и никогда не блокируют `POST /otp/send` и `POST /otp/verify`.

## Этап 2. Ядро OTP и защита (Обязательная часть ТЗ 6 + Автопроверка)

- [x] **Криптография (`app/core/crypto.py`):**
  - Генерация 6-значного кода строго через `f"{secrets.randbelow(1_000_000):06d}"` (без `random`).
  - Хеширование `HMAC-SHA256(HMAC_SECRET, f"{msisdn}:{code}")` — сами коды в Redis не хранятся.
  - Валидация входных данных через Pydantic (`msisdn` и 6-значный `code`).
- [x] **Тестовый транспорт доставки (`app/services/outbox.py`):**
  - На каждую успешную выдачу `/otp/send` атомарно дописывать строку JSON в файл `OTP_OUTBOX` (по умолчанию `outbox/sms.jsonl` в корне репозитория):
    ```json
    {"ts": "2026-11-21T09:00:00+06:00", "msisdn": "996770730000", "code": "012345"}
    ```
  - Сервис этот файл никогда не читает (только append + flush).
- [x] **Атомарный Redis Lua-скрипт для `POST /otp/send` (все расчёты в миллисекундах `now_ms`):**
  - **Проверка блокировки номера:** первым шагом проверить `lock:{msisdn}` — если активна (`now_ms < locked_until_ms`), вернуть **`423 Locked`** (требование сценария `O12`).
  - **Скользящее окно 10 минут (Sorted Set):** при `>= 3` отправках за `600_000` мс возвращать `429` + заголовок `Retry-After`.
  - **Прогрессивная задержка (`30`, `60`, `120` сек в мс):** при `now_ms - last_sent_ms < cooldown_ms` (включая границу `29.999` сек из `O07`) возвращать `429` + `Retry-After`.
  - Сохранение нового хеша в Redis Hash `otp:{msisdn}` с полями `hash`, `expires_at_ms = now_ms + 120_000`, `status = "active"` и **TTL ключа 900 сек** (чтобы надёжно отличать истёкший код `410` от несуществующего/неверного `401`). Повторный `send` перезаписывает и аннулирует старый код.
  - Запись выдачи в `outbox/sms.jsonl` и (при включённом профиле `telecom`) асинхронная постановка задачи в телеком-шлюз.
- [x] **Извлечение `client_ip`:**
  - Читать IP клиента из `X-Forwarded-For` (первый адрес) → `X-Real-IP` → fallback на `request.client.host`, чтобы корректно отрабатывать документационные IP из сценариев жюри (`192.0.2.10`, `198.51.100.20`).
- [x] **Атомарный Redis Lua-скрипт для `POST /otp/verify` (все расчёты в миллисекундах `now_ms`):**
  - **Лимит по IP:** Скользящее окно (Sorted Set `rl:ip:{ip}`) — не более 20 проверок за `60_000` мс по всем номерам, иначе `429`.
  - **Блокировка номера:** Проверка `lock:{msisdn}` — если активна, возвращать `423 Locked`.
  - **Проверка срока и состояния:**
    - если кода нет или `status == "used"` → вернуть **`401 Unauthorized` без инкремента счётчика `fail:{msisdn}`** (критично для `O16`: 20 параллельных `verify` с верным кодом должны вернуть ровно `1 × 200` и `19 × 401`, а не `423`);
    - если **`now_ms >= expires_at_ms`** (строго `>=`, чтобы ровно `120.0` сек в `O03` давали `410`) → вернуть `410 Gone`.
  - **Сравнение за постоянное время:** побайтный XOR по всей длине hex-хеша в Lua без раннего выхода (`break`).
    - Совпало → атомарно установить `status = "used"`, сбросить счётчик ошибок `fail:{msisdn}`, вернуть `200 OK` (гарантирует ровно один успех при параллельных запросах).
    - Не совпало → инкрементировать счётчик ошибок `fail:{msisdn}`; при 5 неверных вводах выставить `lock:{msisdn}` на 15 минут (`900_000` мс) и вернуть `423 Locked`, иначе `401 Unauthorized`.
- [x] **Журнал событий безопасности:**
  - Запись всех событий (`OTP_SENT`, `OTP_VERIFIED`, `OTP_FAILED`, `OTP_EXPIRED`, `MSISDN_LOCKED`, `RATE_LIMITED_SEND`, `RATE_LIMITED_IP`) в Redis Stream `security:events` и структурированный JSON-лог.
  - Гарантия отсутствия самих OTP-кодов в журнале безопасности.

## Этап 5. Реальный телеком-контур (Опциональный бонус, только после Этапов 1–4)

> **Изоляция от автопроверки:** Все телеком-сервисы добавляются в `docker-compose.yml` с `profiles: ["telecom"]` (запуск командой `docker compose --profile telecom up -d`). Обычный `docker compose up` запускает только `otp-api + redis`.

- [x] **Расширение `docker-compose.yml` (`profiles: ["telecom"]`):**
  - `rabbitmq` (`rabbitmq:3-management-alpine`) — AMQP-очереди Jasmin (`:15672`).
  - `smppsim` — операторский SMSC на порту `2775` (протокол SMPP v3.4).
  - `jasmin` (`jookies/jasmin`) — SMS-шлюз, подключённый к `redis` и `rabbitmq`.
  - `jasmin-init` — автоконфигурация через `jcli` (`:8990`): SMPP-коннектор `smppsim:2775`, маршрут `DefaultRoute`, аккаунты `otp_svc` (высокий приоритет, `100 TPS`) и `bulk_mkt` (низкий приоритет, `5 TPS`).
- [x] **Адаптер отправки и биллинг (`sms_dispatcher.py`, `billing_service.py`):**
  - Асинхронная отправка в Jasmin (`http://jasmin:1401/send`) с `validity-period=2`, `dlr=yes`, `dlr-level=2` и `dlr-url=http://otp-api:8000/telecom/dlr`.
  - Сегментация текста (GSM-7: 160 / UCS-2: 70), списание баланса и запись CDR (`SUBMITTED`), обновление по `POST /telecom/dlr` (`DELIVRD` / `EXPIRED` / `UNDELIV`).
  - **Circuit Breaker / Fallback:** при недоступности Jasmin тихий фолбэк без влияния на ответы `/otp/send` и запись в `outbox/sms.jsonl`.
- [x] **Скрипт массовой рассылки (`scripts/bulk_flood.py`):**
  - Отправка пачки из 50 сообщений через `bulk_mkt` (`5 TPS`) для демонстрации приоритета OTP-трафика.

> **Запасной вариант (План Б):** Если `jasmin` или `smppsim` начнут отнимать больше 1.5 часов или нестабильно подниматься в Docker — не тратить время на отладку; либо заменить на лёгкий Python SMPP/RabbitMQ-воркер, либо остановиться на SOC-дашборде (он уже закрывает бонусную часть).
